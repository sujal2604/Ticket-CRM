# Support Ticket CRM

A full-stack customer support ticketing system built with **FastAPI + SQLite + vanilla JS/Tailwind**.

## Features

- Create tickets (customer info, subject, description, auto-generated ID like `TKT-001`)
- List all tickets in a clean table (ID, name, subject, status, priority, date)
- Live search-as-you-type across name, email, ID, and description
- Filter by status (Open / In Progress / Closed)
- Detail view per ticket: update status, assign to a team member, add notes/comments

**Bonus (see "Why this addition" below):** priority levels and a lightweight `assigned_to` field, so a team handling hundreds of tickets a day can triage and split work across agents instead of everyone working one shared, unsorted queue.

## Tech Stack

- **Backend:** Python + FastAPI
- **Database:** SQLite (2 tables: `tickets`, `notes`)
- **Frontend:** Plain HTML + Tailwind CSS (CDN) + vanilla JavaScript (no build step)

## Run Locally

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
uvicorn main:app --reload
```

Open **http://127.0.0.1:8000** — the SQLite file `tickets.db` is created automatically on first run.

## API Endpoints

| Method | Endpoint                | Description                                  |
|--------|--------------------------|-----------------------------------------------|
| POST   | `/api/tickets`           | Create a ticket → `{ ticket_id, created_at }` |
| GET    | `/api/tickets`           | List tickets, optional `?status=` & `?search=` |
| GET    | `/api/tickets/{ticket_id}` | Full ticket detail, incl. notes            |
| PUT    | `/api/tickets/{ticket_id}` | Update `status`, `assigned_to`, and/or add `note_text` |

Interactive API docs are auto-generated by FastAPI at `/docs`.

## Deploying to Railway

1. Push this project to a new GitHub repo (see below).
2. Go to [railway.app](https://railway.app) → **New Project** → **Deploy from GitHub repo**.
3. Railway auto-detects Python. It will use the `Procfile`:
   `web: uvicorn main:app --host 0.0.0.0 --port $PORT`
4. No environment variables are required — SQLite runs on the local filesystem.
   *(Note: Railway's filesystem is ephemeral on redeploys — fine for a demo/assignment; for a real production system, swap SQLite for a managed Postgres instance, which only requires changing `database.py`.)*
5. Once deployed, Railway gives you a public URL — that's your submission link.

## Why this addition (Bonus / Standout)

**What I added:** a `priority` field (Low/Normal/High/Urgent) on ticket creation, and an `assigned_to` field editable from the detail page.

**Why:** the prompt asks what a real team handling hundreds of tickets a day, across multiple clients, would actually need. The single biggest gap in a bare-bones ticket list is that every ticket looks equally urgent and nobody owns it. Priority lets a team triage at a glance; `assigned_to` turns a shared inbox into distributed, accountable work — the minimum needed for actual team collaboration, which the assignment explicitly calls out as an evaluation criterion.

**Trade-off:** I didn't build full user accounts/auth or a formal "teams" table — `assigned_to` is a free-text field rather than a foreign key to a `users` table. That's a deliberate scope cut: it delivers the collaboration benefit immediately without adding login flows, sessions, or a third database table, which the spec explicitly says to avoid ("keep it simple, don't over-engineer the schema"). A real production version would replace it with a proper `users`/`agents` table and role-based auth.
